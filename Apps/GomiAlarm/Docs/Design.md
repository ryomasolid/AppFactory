# GomiAlarm（ゴミの日アラーム）— 設計・画面構成

最終更新: 2026-09-12 / 掲載文は `Store/ASO.md`

> 実装状況: Tuist プロジェクト・モデル・通知スケジューラ・バックグラウンド再構築・周期エディタ・ホーム・全画面（ホーム／予定／カレンダー／設定）・オンボーディング・課金/広告・ストア一式・単体テスト84本まで完了。残るは外部アカウント側の設定のみ。

## 1. 方針

- **自治体データを持たない**。ユーザーが手元の収集カレンダーを見て「種類 × 周期」を登録する。これで全国どこでも使え、保守コストがゼロになる（データ連携型の競合が更新停止で死んでいく領域）。
- **登録は最初の一度だけ**。以後の価値はすべて通知で届く。アプリを開かせる必要がない設計にする。
- 完全オンデバイス（サーバー・アカウント・位置情報なし）。既存3アプリと同じ。
- v1 は **iPhone 専用**（`destinations: [.iPhone]`）。iPad スクショ・レイアウト検証の工数を削る。

## 3. データモデル（SwiftData）

```swift
@Model final class GarbageKind {        // ゴミの種類
    var name: String                     // 「燃えるゴミ」
    var colorHex: String                 // カレンダー/カードの色
    var symbolName: String               // SF Symbols
    var note: String                     // 分別メモ「キャップは外す」
    var eveningHour: Int?                // 前夜通知の時刻（nil=設定の既定値）
    var morningHour: Int?                // 当日朝通知の時刻（nil=既定値）
    var sortOrder: Int
    @Relationship(deleteRule: .cascade) var rules: [CollectionRule]
}

@Model final class CollectionRule {      // 収集の周期（1種類に複数持てる）
    var kindRaw: String                   // weekly / biweekly / nthWeekday / monthlyDay / once
    var weekdays: [Int]                   // 1=日…7=土（weekly は複数選択可）
    var nthWeeks: [Int]                   // nthWeekday 用（1..4, 5=最終）
    var dayOfMonth: Int?                  // monthlyDay 用
    var anchorDate: Date?                 // biweekly の基準日 / once の日付
}

@Model final class DoneRecord {          // 「出した」記録（ストリーク表示用）
    var kindID: UUID
    var date: Date
}
```

周期の種類（ここが競合との実用差）:

| 周期 | 例 | 実装 |
| --- | --- | --- |
| `weekly` | 毎週 月・木 | 曜日ごとに繰り返しトリガ |
| `biweekly` | 隔週 水（基準日から2週ごと） | 日付列挙 |
| `nthWeekday` | 第2・第4 水曜 / 最終 金曜 | 日付列挙 |
| `monthlyDay` | 毎月15日 | 日付列挙 |
| `once` | 粗大ごみ 10/3 | 単発トリガ |

## 4. 通知設計（ここが本アプリの心臓）

**制約: iOS の保留ローカル通知は1アプリ64件まで**（超えた分は登録されない）。前夜＋当日朝の2段で件数が倍になるため、素朴に全部登録すると即あふれる。

スケジューラの方針（実装済み: `Services/NotificationPlanner.swift` / `NotificationScheduler.swift`）:

登録内容を決める計算（`NotificationPlanner`）と、実際に `UNUserNotificationCenter` へ積む処理（`NotificationScheduler`）を分けてある。前者は副作用ゼロの純粋関数なので、本数・文面・上限の扱いを単体テストで固定できる。

1. **モードA（永続）**: すべてのルールが「毎週」で、祝日スキップがオフのとき。
   `UNCalendarNotificationTrigger(weekday+hour, repeats: true)` だけで表現でき、最大でも 7曜日 × 2タイミング。一度登録すれば**再構築が不要**。
   ※ 前夜通知は「翌日が収集日」なので **weekday を1つ前にずらす**（月曜収集 → 日曜20:00）。
2. **モードB（窓）**: 隔週／第n曜日／毎月◯日／単発が1つでもあるか、祝日スキップがオンのとき。
   くり返しで表現できないので、今日から **120日分の具体日を列挙**して個別登録する。
3. **同じ日・同じ時刻の種類は1本にまとめる**（「今日は 燃えるゴミ・プラ の日」）。
   本数の節約になるうえ、通知が連続で2回鳴るうるささも避けられる。種類ごとに通知時刻を変えている場合だけ別建てになる。
4. **予算管理**: 上限は **60件**（64件きっかりではなく余裕を持たせる）。超える場合は**鳴る日時が近い順**に残す。
   切り捨てが起きたら `NotificationPlan.truncated` が立つので、設定画面で警告を出す。
5. **再構築のタイミング**: アプリ起動時・フォアグラウンド復帰時・種類や設定の変更後に「全削除 → 再登録」。差分更新はバグの温床なうえ、保留通知は鳴るたびに減っていくので、毎回作り直す方が安全。
   入口は `Services/NotificationRefresh.swift` に一本化してある（SwiftData から読む → 組み直す → 次のBG実行を予約 → `RefreshStatus` を保存）。
   - **自動実行では許可ダイアログを出さない**（`requestingAuthorization: false`）。許可はオンボーディングでだけ求め、起動のたびにダイアログが出る事故を防ぐ。
   - モードBは窓が枯れるので `BGAppRefreshTask` で組み直す（`Services/BackgroundRefresh.swift`）。
     SwiftUI の `.backgroundTask(.appRefresh:)` を使い、ハンドラ登録・期限切れ処理・`setTaskCompleted` は SwiftUI に任せる（AppDelegate を持たずに済む）。
   - **予約の間隔**（`Services/BackgroundRefreshPolicy.swift`）: カバー範囲の**半分**を過ぎたら組み直す。下限1日・上限7日。
     実行が遅れても残り半分の通知は生きているので取りこぼさない。モードA（永続）と未許可のときは**予約しない**＝OSの実行枠を無駄に使わない。
   - `Info.plist` に `BGTaskSchedulerPermittedIdentifiers = ["tech.sesame.gomialarm.refresh"]` と `UIBackgroundModes = ["fetch"]` を設定済み。
     識別子が `BackgroundRefresh.taskID` とずれると**起動時にクラッシュする**ので、変更するときは必ず両方を直す。
   - 実機での動作確認: デバッガで一時停止し
     `e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"tech.sesame.gomialarm.refresh"]` を実行する。
     シミュレータでは BGTaskScheduler が使えないので、`schedule(at:)` は false を返すだけで害は無い。
6. **祝日スキップ**（設定でON時）: 祝日データは表を同梱せず、**祝日法のルールから計算する**（`Services/HolidayCalendar.swift`）。
   固定日・ハッピーマンデー・春分／秋分（1980〜2099年で使える近似式）に加え、**振替休日**と**国民の休日**（2026年の 9/22 など）も導出する。表を持たないので期限切れも更新作業も発生しない。臨時の祝日だけ `extraHolidays` に手で足す。
   - 自治体によって祝日も収集するため **デフォルトOFF**。設定画面に「お住まいの地域が祝日も収集する場合はオフ」の注記。
7. **通知アクション**（PestMap の categories を流用）: `出した` / `1時間後に再通知`。`出した` で `DoneRecord` を追加。

通知文例:
- 前夜: タイトル「明日は 燃えるゴミ の日」／本文「今のうちにまとめておきましょう。（キャップは外す）」
- 当日朝: タイトル「今日は 燃えるゴミ の日」／本文「8:00までに出しましょう。」

### 5.2 ホーム（今日/今後）— 実装済み（`Views/HomeView.swift`）

アプリを開いた瞬間に答えが出る画面。ここだけでアプリの価値が成立する。

- 今日の収集がある日は**種類ごとに色ベタ塗りの大カード**（種類が複数ならカードを積む。
  1枚に混ぜると色が競合して、どれを出すのか読み取りづらくなる）。
- 収集が無い日は「今日は収集なし」＋次の収集日。**開いて空振りにしない**。
- 予定の組み立ては `Services/UpcomingSchedule.swift`（純粋ロジック）。
  **通知と同じ `ScheduleCalculator` と祝日設定を使う**のが要点で、
  画面の予定と実際に鳴る通知が食い違うとアプリ全体が信用されなくなる。
- ストリークは `Services/StreakCalculator.swift`。その日の種類を**すべて**出して1回とカウントし、
  今日ぶんは未チェックでも連続を途切れさせない（これから出すため）。
  単位は設計時の「週」ではなく**「回」**にした（1週に複数回の収集があるため週だと数が合わない）。
- 「出した」は `DoneRecord` に記録。カードは出し終えると少し落として、残りが目立つようにする。

### 5.3 予定（種類の一覧・編集）— 実装済み（`Views/ScheduleListView.swift` / `KindEditorView.swift`）

- 編集は `Models/KindDraft.swift`（値型）の上で行い、**「保存」を押したときだけモデルへ書き戻す**。
  SwiftData のモデルを直接編集すると、キャンセルしたつもりの変更や作りかけの空データが残る。
- **保存できる条件は「名前」＋「成立している周期が1つ以上」**。周期の無い種類を作れてしまうと、
  登録した本人は設定したつもりなのに通知が来ない状態になる。曜日未選択の作りかけルールは保存時に捨てる。
- 色とアイコンは `Models/KindPalette.swift` から選ばせる（自由入力にすると、
  白や極端に薄い色が選ばれてホームのカードの文字が読めなくなる）。
- 通知時刻は種類ごとに上書きできる。`nil` は「設定の既定に従う」の意味で、既定値そのものは持たせない
  （持たせると、設定を変えても古い値が残る）。
- 並べ替え可。並び順は通知文（「燃えるゴミ・プラ」）とホームの色ドットの順にそのまま出る。
- 種類を消すときは、その種類の `DoneRecord` も一緒に片付ける（種類IDで持っているだけなので孤児になる）。
- **未実装**: 無料版の「3種類まで」の制限。StoreManager 未移植のため、
  いま入れると解除手段が無く、デモデータ（4種類）も壊れる。課金の移植と同時に入れる。

周期エディタ（実装済み: `Views/RuleEditorView.swift`）:

```
┌────────────────────────────┐
│ キャンセル  収集の周期   保存  │
│ 周期                        │
│ [毎週][隔週][第1・第3]        │  ← プリセット（幅が足りなければ折り返す）
│ [第2・第4][詳細]             │

│  10月14日(水)               │

│  第2・第4 水曜               │
└────────────────────────────┘
```

- **プリセットを最初に並べる**。周期の種類→第n→曜日と3段階で選ばせると離脱するので、
  実際に使われる4つ（毎週／隔週／第1・第3／第2・第4）を入口にし、
  **「第2・第4」→「水」の2タップ**で作れるようにした。残りは「詳細」に押し込む。
- **隔週は「次の収集日」を1つ選ぶだけ**。曜日と基準週の両方をその日付から導く（二重入力を避ける）。
- **保存前に「次の収集日」を3つ出す**。ゴミ出しは間違えても1週間後まで気づけないので、
  その場で確認できることが安心につながる。この表示は `ScheduleCalculator` をそのまま呼ぶので、
  プレビューと実際の通知がずれない。
- プリセットの復元は `Models/RulePreset.swift`（純粋ロジック・テスト済み）。
  プリセットで表現できない組み合わせ（第2のみ・最終◯曜・毎月◯日・単発）は「詳細」に落として設定を壊さない。

## 6. 無料 / Pro の境界

| | 無料 | Pro（買い切り 300円） |
| --- | --- | --- |
| ゴミの種類 | **3つまで** | 無制限 |
| 周期（隔週・第n曜日を含む） | すべて利用可 | 同じ |
| 前夜＋当日朝の2段通知 | ○ | ○ |
| カレンダー | ○ | ○ |
| 祝日スキップ | × | ○（設定タブのトグル。Pro でなければタップで課金画面へ） |
| 広告 | バナー表示（全タブ共通で最下部に1つ） | 非表示 |

- **周期の種類は無料で全部開放する**。「第2・第4水曜」が使えないと実用にならず、そこを塞ぐと離脱するだけで課金に繋がらない。課金動機は「種類が足りない」「広告が邪魔」に寄せる。
- 3種類は「燃えるゴミ／資源／プラ」でちょうど埋まる数。缶・瓶や粗大ごみを足したくなった瞬間が購入タイミング。
- ウィジェット／ロック画面（WidgetKit）は **v1.1** の目玉。未実装機能をPro特典として売らない（審査NG）。
  祝日スキップは設定タブで実装済みだが、**課金画面の訴求からは外している**（3つに絞った方が伝わるため）。
- 課金まわりの実装: `Services/StoreManager.swift`（StoreKit 2・買い切り）／`Views/PaywallView.swift`／
  上限の判定は `Models/ProLimits.swift`（純粋ロジック・テスト済み）に集約する。
- 広告: `Services/ConsentManager.swift`（UMP → ATT → AdMob 初期化）＋ `Views/BannerAdView.swift`。
  バナーは `ContentView` の TabView の下に**1つだけ**置く（画面ごとに置くと重複・二重表示を招く）。
  `store.isPro` か `-hideAds` のときは出さない。

## 7. スクショ用の起動引数（`Launch.swift`）

既存アプリと揃える。`-hideAds` / `-demo` / `-showPaywall` / `-forceOnboarding` / `-startTab <today|schedule|calendar>` / `-showRuleEditor`（周期エディタを直接開く）/ `-showKindEditor`（種類編集を直接開く）。
※ PhotoCleaner だけ Paywall 表示が `-screenshotPaywall` になっている。新規は TeikiCheck 側の `-showPaywall` に統一する。

`-demo` で投入するデモデータ: 燃えるゴミ / 資源ごみ(第2・第4 水) / プラ(毎週 金) / 缶・瓶(隔週 火)、
直近8回ぶんの `DoneRecord`（ストリーク表示のため）。

**燃えるゴミの曜日は実行日の曜日に合わせて生成する**（今日＋3日後）。
ホームの主役は「今日出すゴミ」の大カードなので、いつ撮影しても必ず埋まるようにしてある。

## 9. リスクと対策

| リスク | 対策 |
| --- | --- |
| シートに環境（StoreManager）が伝わらず課金画面で落ちる | シートの中身に `.environment(store)` を明示的に渡す。実際にこれで起動時クラッシュを踏んだ |
| 初期登録の面倒さで離脱 | オンボーディングのテンプレ投入を必須動線に。登録0件のホームは「テンプレから作る」CTAを大きく出す |
| 通知が来ない＝価値ゼロなのに、許可されない | 許可前に「何の通知が何時に届くか」を具体例で見せる。拒否時は設定アプリへの導線を常設（設定＋ホームにバナー） |
| 64件上限に気づかず通知が消える | 予算管理を実装し、上限に達したら設定画面に警告表示。テストで種類20件×複数周期のケースを検証 |
| 祝日の扱いが自治体で違う | デフォルトOFF＋注記。説明文にも免責 |
| 審査（通知許可ボタンの文言） | PhotoCleaner のリジェクト事例を踏まえ、システムダイアログを模した文言を避ける |
| 自治体データを持たないことが弱点に見える | ASO とスクショで「全国どこでも使える／自治体を選ぶ必要なし」を明示 |
